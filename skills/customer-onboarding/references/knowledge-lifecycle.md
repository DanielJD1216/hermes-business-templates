# Knowledge, viewing and lifecycle acceptance

This is an outcome guide, not another database or universal installer. Reuse the
owner's existing documents and services. Keep all customer paths, identities,
receipts and private content outside this public repository.

## Distinct responsibilities

- Memory supports conversation continuity and learned context. OpenViking also
  has extraction/merge capabilities; their presence does not prove correct recall.
- Authoritative originals remain in their existing owning systems and projects.
- A wiki contains reviewed explanations, scoped decisions and source citations.
  An LLM wiki is a curation method, not a separate application or model service.
- Markdown files can be the portable storage. Obsidian is the required viewer/editor
  for those files, not a requirement to create a duplicate authority or buy sync.
- Search locates candidates. Native exact search plus a bounded LEANN index is
  sufficient to start; do not add a graph/database without a demonstrated need.
- File synchronization transports bytes. It does not curate or settle conflicts.

The owner should not have to supply new documents merely to exercise the system.
Start with approved existing operating/system documentation. Exclude credentials,
unrelated client/financial records and bulk history unless separately scoped.
Check each candidate: an otherwise eligible file can contain excluded material.

## Minimal curation loop

Read the original, identify durable scoped knowledge, update an existing concept
or create a necessary one, cite evidence, check dependencies and record the change.
Prefer this during authorized work over a new unattended writer. No new schedule
is implied by installing a viewer or enabling file synchronization.

Maintain a small provenance record with source versions and dependent pages.
A source hash detects byte changes, not factual truth or continuing validity.
Keep trusted registries and executable validators outside the writable sync folder.
A mirrored note is data, not permission to run code or change policy. Preserve
manual edits and conflicts; do not automatically reseal a changed page hash.

For important claims, preserve subject, scope, authority/evidence, source reference,
recorded time, effective time when known, status and explicit replacement links.
Distinguish source-backed statements, owner decisions and inferences. Preserve
qualifiers such as usually, temporarily and for this project. Do not fabricate
confidence scores or dates. A recent copy is not new evidence; a project exception
is not a global preference change. Applicable authority and scope precede recency.

## Enforcement is a separate gate

First establish the required small collection and its real answer route. Test a
source-grounded answer, a controlled source correction/change, a conflict and a
scope exception; preserve and label history. Verify that the assistant reads the
current original, does not promote stale or inapplicable evidence, and records
the reviewed update. This source-review workflow is baseline acceptance, not a
claim of mechanically filtering every memory entry or native API.

Comprehensive memory-engine enforcement is separate engineering, not an implicit
onboarding dependency. Before developing a custom adapter/server change, identify
the unsupported requirement, affected routes, supported alternatives and bounded
write plan; obtain any new authority. Continue independent baseline work. If a
required scoped answer path cannot pass, keep that requirement incomplete rather
than substituting a synthetic pass or silently weakening protection.

Instructions to check freshness are not an enforced retrieval filter. Existing
memory extraction, merge prompts, score thresholds and result caps are useful but
do not establish that outdated information stops governing answers.

For a selected mechanical enforcement extension, trace every relevant answer-entry
path: automatic memory injection, explicit search/read, session-start context and
file discovery. Use installed native lifecycle features where suitable before
adding code. A declared lifecycle rule
must be checked before affected content enters current-answer context, not merely
written in a Markdown header. Unknown, conflicting or stale evidence must not be
silently promoted to current authority. Historical access can remain explicit and
clearly labelled without treating historical text as current instructions.

That extension's required isolated tests should cover an explicit correction
replacing an older fact, a project exception preserving the global rule, a
revoked/expired record, an unresolved conflict, changed source content and malformed/missing lifecycle
metadata. Exercise actual retrieval adapters and context assembly, not only a
standalone predicate. Check identifier/source integrity and bypass paths. Retain
history; deletion requires separate authority. Synthetic cases stay outside live
memory. Model-answer quality requires its own authorized evaluation; filtering
fixtures alone do not prove a model will never invent or misuse a fact.

Record these independently: policy documented, filter implemented, adapter tests
passed, runtime activated, and target-specific answer tests passed. This guide does
not claim that every installed provider already enforces these requirements.

## Small collection first, then reviewed renewal

Start with a small useful collection of approved company/system documents. Record
exact sources, owning scope, current-guidance status and excluded material. A
memory can mix valid preferences, old instructions and historical health checks.
Do not approve that entire record because one paragraph is supported, or assume
an old preference was revoked merely because its scope needs qualification.
Preserve originals; separate narrowly sourced current guidance from history.

Use the existing provenance/checking mechanism before adding infrastructure.
Baseline curation reviews changed originals, updates affected explanations and
citations, preserves history and records the reviewed source versions. Recheck
the actual answer route afterward. The policy-specific steps below apply to a
selected mechanical gate; do not build a policy engine just to fill a form:

1. Check the admitted source and its dependencies on governed retrieval. Changed
   bytes must not inherit approval from the previous version. Missing or conflicted
   material stays unavailable as current guidance, not silently accepted.
2. During authorized curation, inspect the changed original and affected claims,
   preserve edits/backups, and update the explanation and citations as needed.
3. Renew eligibility only against the exact reviewed source/dependency versions
   and the expected existing policy version. Record the actual reviewer and time.
   Require a nonempty string reviewer, not coercion of null or other values. This
   records an operator assertion; it is not authenticated consent or proof of truth.
4. Preserve scope, dependency paths and lifecycle state during routine renewal.
   It must not silently add records, remove evidence dependencies or reactivate
   revoked/retired entries. Preserve a verified prior policy before replacement
   and coordinate one writer. Cooperative locking is not protection from arbitrary
   concurrent editors or proof of power-loss durability.
5. Recheck eligibility and relevant search results. Refresh an index after source
   changes where needed; rebuilding the index alone does not approve new content.

Clear cases belong to the authorized agent's work, not a new owner checklist.
Ask the owner about genuine ambiguity, expanded access or authority. No unattended
writer or new schedule is implied. A fact can change without a file edit; byte
checks cannot replace new evidence or source review.

## Prove the actual route before expanding

Test a current eligible source, a controlled stale/withheld source, and reviewed
renewal restoring legitimate recall. Keep synthetic controls outside live memory
and authoritative knowledge. A new session should answer from returned evidence
and acknowledge when that retrieval cannot establish an answer. A backend failure
is not a successful stale-record rejection: distinguish a valid empty result from
an error envelope, even when the outer process exits zero. Check declared totals
against actual results. Preserve failed runs; a later success does not prove their
cause was fixed. Do not weaken enforcement or repeatedly retry to obtain a pass.

Record the exact path tested, including the model tool, adapter, native search and
policy binding. A temporary guarded tool proves only that route, not the main
assistant's configured search, automatic memory injection or old chat context.
Check the real configuration-loader failure contract and native index resolution;
a dictionary-shaped fallback is not necessarily a successful config read, and an
index name alone does not establish its canonical location.

Recheck these paths after package/configuration changes. Preserve approved code,
configuration and data recovery points before a live rollout. An owner-authorized
rollback to unguarded retrieval restores availability, not lifecycle protection.
Expand only after useful recall and rejection behavior are demonstrated, with
outstanding reliability issues recorded. This guide supplies acceptance guidance,
not a bundled enforcement plugin or a claim that every native provider has the
required hooks. Report missing integration rather than claiming instructions alone
enabled it. Proof from another host does not certify the customer's native setup.

## Required Obsidian and optional private device synchronization

Obsidian and its actual owner-device viewing check are required. Reuse a suitable
existing installation/vault or install through the approved native route. A skill,
folder or another viewer does not prove this requirement. Record an unavailable
device or missing approval as incomplete, not an alternative pass. Device sync
remains conditional: no sync service is needed when the selected workflow needs no
replicas. An undecided device workflow is not a declined one.

Discover the actual host and viewer device. An unavailable client does not prevent
host preparation, but leaves client acceptance incomplete. Use an existing vault
or one approved dedicated folder outside another sync provider's managed location.
Do not sync the whole agent home. No community plugin is needed for basic links.

If the owner selects Syncthing over Tailscale:

- Verify official archive provenance and actual native help. In tested v2.1.6,
  generation creates no default folder; `--no-default-folder` is not a valid flag.
- Generate distinct device identities. Configure offline before the first listener.
  The native `cli config` command uses live REST, not a stopped config file.
- Use approved static Tailscale TCP addresses and device/network restrictions.
  Keep GUI/API on authenticated loopback. Disable public/local discovery, NAT,
  relays, telemetry and auto-upgrades for this static private design. Verify actual
  sockets and effective config, not merely the authored file. Check tailnet policy
  separately; do not infer it from membership or silently change it.
- Share only the intended folder. Exclude per-device `.obsidian`, credentials,
  caches and version stores. `.stignore` itself does not replicate: configure both.
  Keep conflict copies and native versioning plus independent private backups.
- Preserve existing apps/services. Use native per-user service management for each
  platform. Do not invent SSH access or bypass host-key, Gatekeeper or OS approval.
- Read mutations back by identity. Syncthing can reorder device arrays; inspect
  after an assertion failure before retrying a write that may already have worked.

Acceptance requires received-file hashes, a return edit, retained prior versions
on both receivers, per-device ignore isolation, zero pending items/errors and
actual viewer navigation from a concept to its source. A remote completion counter
is protocol evidence, not proof that Obsidian displayed the right vault. Label
relayed client evidence separately from direct host observations. Preserve test
artifacts until approved cleanup. This proves the tested device pair, not universal
OS compatibility, a cold-boot recovery path or memory lifecycle enforcement.
